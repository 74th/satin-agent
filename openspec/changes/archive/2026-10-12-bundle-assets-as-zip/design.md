# Design

## Context

動機は`proposal.md`を参照。関係する現状は次のとおり。

- `publish_gcs()`（`assets/gcs.py`）は、`Assets.files()`の各ファイルを`ObjectStore.write()`で1つずつ書き、アセットにないオブジェクトを消し、最後に`manifest.json`（相対パス → sha256）を書く。
- `fetch_assets()`（`runtime/assets.py`）は、マニフェストを読み、各ファイルを取り出してsha256を照合し、一時ディレクトリ（`.satin/assets.tmp`）に書いてから`.satin/assets`と入れ替える。照合に失敗したら`AssetMismatchError`になり、entrypointは終了コード3で止まる。
- `ObjectStore`のport（`read` / `write` / `delete` / `list`）と、`GcsStore`は、キーと中身のバイト列だけを扱う。zipにしても変更は要らない。
- `GcsStore.read()`が使う`download_as_bytes()`は、既定でGCSのチェックサム（crc32c）を検証する。
- (A)のSkillsは、Skills APIで別に配る。GCSのアセットは、(A)でも`.satin/assets`に取り出されるが、Skillsとして使うのは(B)だけ（`place_for_claude_code`）。

## Goals / Non-Goals

**Goals:**

- アセットの取得と更新を、1オブジェクトにする（原子的にする）。
- 壊れた配布や不正なzipを、ワーカーの起動前に検出して止める（今の「不一致なら起動しない」を保つ）。
- 変更を`assets/gcs.py`と`runtime/assets.py`に閉じ込める。

**Non-Goals:**

- アセットの差分配布（変更したファイルだけの更新）。
- 配布内容のバージョン管理（世代の保持・ロールバック）。
- 署名など、GCSへの書き込み権限を持つ者による改ざんの検出。従来のマニフェストも、同じ権限で書き換えられるので、防げていなかった。
- 古い配置（`manifest.json`と個別のファイル）を新しいイメージで読む互換。

## Decisions

### 1. 配置は`assets.zip`の1オブジェクトにする

配布先のprefix直下に`assets.zip`だけを置く。zipの中は、アセットディレクトリと同じ相対パス（`skills/<name>/...`、`CLAUDE.md`、`startup.sh`、`mcp.json`）にする。`Assets.files()`の内容をそのまま使う（`manifest.json`は入れない）。

他の案は次の理由で採らない。

- **zipと`.sha256`の2オブジェクト**: 2つを書く間に、不整合を見る時間ができる。1オブジェクトにする目的に反する。
- **tar.gz**: 標準ライブラリで扱えるが、zipのほうがエントリごとのCRCがあり、ランダムアクセスでき、利用者が指定した形式でもある。

### 2. 同じ内容は同じバイト列にする

`zipfile`でエントリをパスの昇順に書き、更新日時を固定値（1980-01-01）、外部属性を固定（ファイルは0644、`#!`で始まるファイルは0755）、圧縮はdeflateにする。これで、再配布しても内容が変わらず、差分の確認と配布の冪等性が簡単になる。実行ビットは、`startup.sh`を`sh`で実行する現状では要らないが、Skillのスクリプトを直接実行できるよう、先頭が`#!`のファイルにだけ付ける（アセットの読み込みは、元のファイルの権限を持たないため、中身で判断する）。

### 3. `manifest.json`は廃止し、zipの検査で置き換える

Sandboxは、zipを取得するとき、GCSのクライアントがcrc32cを検証する（転送の破損を検出）。展開前に`ZipFile.testzip()`でエントリごとのCRCを確かめ、`namelist()`の各パスを検査する。

- 絶対パス、`..`を含むパス、バックスラッシュを含むパスは、展開先の外へ出る（zip slip）ので、1つでもあれば全体を拒否する。
- 検査は、一時ディレクトリへ展開する前に済ませる。展開は一時ディレクトリで行い、成功したら`.satin/assets`と入れ替える（今の方式のまま）。

エラーは、`AssetMismatchError`を`AssetBundleError`に置き換える（壊れたzip、不正なパス、`assets.zip`がない、のどれも同じ例外にする）。entrypointの終了コード3、ログの形式は変えない。

### 4. 古い配置は、配布時に削除し、新しいイメージは読まない

`publish_gcs()`は、`assets.zip`を書いた後に、それ以外のオブジェクトを全て消す（今の「アセットにないファイルを削除」と同じ順序・同じ考え方）。`assets.zip`が書けなかったら、何も消さない。新しいイメージには、古い配置を読むフォールバックを入れない。

### 5. 切り替えの手順

配布とイメージの入れ替えを近い時間に行う。順番は次のとおり。

1. 新しいランタイムイメージとappイメージをビルド・pushする。
2. `satin publish --target gcs`で、`assets.zip`を書き、古いオブジェクトを消す。
3. `scripts/deploy.sh`で、オーケストレータ・Botを新しいイメージにする。
4. 古いイメージで作られたSandbox（Suspended）は、再開すると古いイメージが新しい配置を読めず失敗する。`satin sandbox gc --all`で消す（開発用クラスタでは保持期限が2時間）。

手順3の前に新しいSandboxが作られると失敗するので、手順2と3の間は短くする。

## Risks / Trade-offs

- [切り替えの間、新旧のSandboxが失敗する] → 手順を決めて短くする。開発用クラスタのみで運用しており、保持期限も短い。手順をREADMEに書く。
- [zipの展開で、展開先の外へ書き込まれる（zip slip）] → 展開前に全パスを検査し、1つでも不正なら全体を拒否する。テストで確かめる。
- [アセットが大きくなると、1回の取得が大きい] → 今も全ファイルを毎回取り出しており、総量は変わらない。1オブジェクトにするほうが、要求の数は減る。
- [配布内容の部分的な破損をファイル名で特定できない] → 不一致のファイル名を出す今のエラーより情報が減る。zipの`testzip()`は、壊れたエントリの名前を返すので、それを出す。
- [`manifest.json`のハッシュを使う機能が他にある] → 調べた範囲では、`commands.py`の表示（ファイル数）だけ。ファイル数は、zipのエントリ数から出す。
